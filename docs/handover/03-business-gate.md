# 03. 업무 개발 내용: 경비대 반출입 시스템

기준 시점: 2026-10-23. 첫 업무 저장소에서 개발할 업무입니다. 출처는 사용자가 준 기존 DB 스크립트, 업무개발 중요사항, 기존 화면 캡처 8장, Confluence 저장본(업무 설명 PPT 본문)입니다. 원본에 있는 서버 주소, DB 계정, 담당자·사용자 이름, 사업자번호는 옮기지 않았습니다.

## 1. 기존 시스템

- 기존 시스템은 Java 1.7, JSP, 전자정부 프레임워크 3.8, jqGrid 4.5.1, Tomcat 8.0, MSSQL 2008로 만들어져 있습니다. DB는 `ivdooinfo`, 스키마는 `dooinfoiv`·`dooinfo`입니다.
- 연계 대상은 EAI-SAP(웹서비스/RFC)와 ADMaster(사용자·부서)입니다. 사용자·부서는 링크드 서버 배치 `ADM_DOODREAM_INTERFACE_BATCH_STR`로 가져옵니다.
- 외부 사용자는 별도 로그인 페이지로 들어옵니다. 프레임워크의 협력사 전용 로그인으로 대체합니다.
- 경비대 출입문은 정문, 후문, 창고 3곳입니다. 경비원이 출력물의 바코드를 스캐너로 읽어 처리합니다.
- 업무 원칙: 모든 자재 반출은 당일 반출·확인하고, D+3이 지나면 자동 반려합니다.

## 2. 사용자가 정한 업무 개발 규칙 (업무개발 중요사항 원문 요지)

1. 기존 소스(SQL 매퍼)와 SQL 스크립트(`DB_SP_FN_infoiv.sql`)를 분석해 **쓰지 않는 TABLE·SP·FN을 삭제**합니다.
2. 기존 소스의 쿼리는 **신규 프레임워크 규칙(SP 표준)에 맞춰 새로 작성**합니다.
3. 기존 화면별로 화면과 DB 데이터 흐름을 정리(문서화)해 화면 이관에 씁니다. **업무 테이블은 이름을 그대로 씁니다**(기존 SQL을 그대로 쓰기 위함). 튜닝이 필요한 곳은 가이드를 따로 씁니다.
4. 관리 화면과 공통 데이터(사용자, 권한, 메뉴, 공통코드 등)는 **신규 프레임워크 구조로 데이터를 변환**해 넣습니다(이관한 데이터도 신규 코드 규칙을 따르게).
5. 업무 화면 7개(통합반출접수, 멀티반출접수, 반출이력조회, 통합반입접수, 멀티반입접수, 반입취소, 반입이력조회)는 UI를 기존과 비슷하게 하되 **BASE FORMAT(표준 화면 틀)은 건드리지 않습니다.**
6. 데이터 마이그레이션은 **기존 DB 위에 신규 테이블을 추가**하는 방식입니다. 공통코드 같은 기준정보는 개발 중 미리 변환·검증한 뒤 운영 DB로 옮깁니다. 그래서 **사용/미사용/신규 TABLE·SP 정리표와 마이그레이션 계획서**가 필요합니다.
7. 업무 전체 설명은 사용자의 Confluence REFACTORING 페이지에 있습니다(클라우드에서는 열 수 없음).

## 4. 업무 흐름

### 반출

1. 원천 시스템(SAP MM / MM_INVOICE / EL, ERP_SD, ERP_IV_PDC, MES 등)이 반출증을 발행하면 `CARRY_OUT10`(헤더)·`CARRY_OUT30`(상세)에 들어옵니다(SAP은 EAI 경유, MES는 직접 INSERT). 구분은 `SYS_ID`/`SYS_NM`입니다.
2. 경비대가 바코드(문서번호)로 조회하고 출력물과 DB 내용을 비교합니다.
3. 일치하면 [경비대 통과] → 상태가 반출완료가 됩니다. `SYS_NM`이 SAP_MM 계열이면 EAI 웹서비스 `DIMM_DOOINFO_SEND_GATE_OUT`, SAP_EL이면 `DIMM_SEND_GATE_OUT_EL`로 SAP에 통과 정보를 보냈습니다. **신규에서는 "전송 대기" 표시 → EAI 수집으로 바꿉니다(3장 결정).** ERP_SD·MES는 상태만 갱신하고, ERP_IV_PDC는 경비대 처리가 없습니다.
4. 불일치하면 반출불가 처리 + 사유 입력(전자결재 아님).
5. 배치: 매일 08시 `CARRY_OUT10_OUTRSVDT_RETURN_BATCH_STR`가 반출일이 지난 건을 반출불가로 바꿉니다 → 프레임워크 스케줄러 작업으로 이관.
6. 반출 취소(운영 요청 시): `CARRY_OUT10`의 경비 처리자·처리일·상태를 비워 반출예정으로 되돌립니다. 상태값은 반출예정, 반출완료, 반출불가입니다.

### 반입

1. 경비대가 바코드를 스캔하면 바코드 체계로 구분해 **SAP을 실시간 조회**합니다(EAI).
   - `IV`로 시작: MM 반입 (`DIMM_PURCHASING_154` / `Z_MM_DOOINFO_NOTIFICATION`, 1 조회 · 2 처리 · 3 취소). 취소 가능.
   - `1`로 시작 + 10자리: MM 재반입. 취소 불가.
   - `DD`(불량, QM) / `DS`(결품 반납, MM): MM_RETURN (`DIMM_PURCHASING_209` / `Z_MM_RET_GR_FACTORY_GATE`). 취소 불가.
   - `IFFIV`(사무용품) / `SERIVO`(현장용품): EAI로 DB에 들어온 데이터만 처리(`CARRY_IN*_KEPOH`).
2. [반입신고] → EAI로 SAP에 전송해 반입완료 → `CARRY_IN10`/`CARRY_IN30`에 기록, 로그 `CARRY_IN_LOG`.
3. 데이터가 없거나 불일치하면 취소합니다. 화면 취소는 MM 반입 건만 가능하고 사유를 입력합니다. 나머지는 SR로 처리합니다.

바코드 접두어 규칙, 원천 시스템 구분(`SYS_ID`/`SYS_NM`/`SYS_GBN`), EAI 인터페이스 이름은 **공통코드·설정으로** 두고 코드에 쓰지 않습니다(VOC: 새 원천 시스템 추가 시 수정이 필요했음).

### 신규 구조 원칙 (설계서 7장 예외 + 제안)

- 신규 업무 SP는 업무 스키마에 둡니다(제안: `GAT`). 예: `GAT.USP_CARRY_OUT_GET`, `GAT.USP_CARRY_OUT_PASS_EXEC`, `GAT.USP_CARRY_OUT_GET_LIST`. 기존 테이블은 `dooinfoiv.CARRY_OUT10`처럼 그대로 참조합니다.
- 앱 DB 계정에는 `dooinfoiv` 테이블 직접 권한을 주지 않고 SP로만 접근합니다(소유권 체인). 스키마 소유자가 다르면 체인이 끊기므로 배포 때 확인합니다.
- 동시성·감사·회사 범위 컬럼은 기본으로 추가하지 않고, 필요한 테이블만 마이그레이션 계획서에 적어 결정합니다.
- 기존 DB 위에 `FW`·`LOG`·`GAT` 스키마를 얹습니다. SQL 프로젝트 게시 설정 `DropObjectsNotInSource=False`, 기본 정렬 `Korean_Wansung_CI_AS`가 맞는지 확인합니다. 기존 테이블은 SQL 프로젝트에 참조(또는 별도 dacpac)로 넣어 빌드 검증을 받습니다.
- 기존 데이터의 `1900-01-01`(빈 날짜)은 신규 SP에서 NULL로 돌려줍니다.
- 개인정보: `ADM_EMP10`에 자택·휴대전화·메일 등이 평문으로 있습니다. FW로는 필요한 항목만 옮겨 암호화하고, 기존 원본의 처리(삭제 또는 마스킹) 계획을 마이그레이션 계획서에 넣습니다.

## 8. 진행 순서 (제안)

1. 업무 저장소 만들기(04 문서) + 미확인 1번(앱 소스) 받기.
2. 사용/미사용/신규 TABLE·SP·FN 정리표 작성.
3. 마이그레이션 계획서: 관리·공통 데이터 변환 규칙(코드, 메뉴, 권한, 사용자·부서), 검증 방법, 개발 DB 사전 변환·검증, 운영 이관 순서, 되돌리기, 기존 객체 삭제 시점.
4. 화면별 화면·데이터 흐름 문서(7개) + 튜닝 가이드.
5. 기준정보 변환 스크립트(코드 → 메뉴 → 권한 → 사용자) 작성과 개발 DB 검증.
6. 업무 화면 이관: 반출 3개(통합 → 멀티 → 이력) → 반입 4개(통합 → 멀티 → 취소 → 이력). 화면마다 기능 PR, 단위 테스트, SP 통합 테스트 코드 포함.
7. 배치 이관(반출 기한 초과 반려), 대시보드 위젯(오늘 반출·반입 현황 등, 필요 시).
8. 업무 단계 종료 통합 테스트 → 운영 이관 리허설.

프레임워크 쪽 선행 작업(프레임워크 저장소에서): AD SSO·조직 동기화, 외부 API 송신(반입 실시간 조회가 필요하면), 업무 저장소용 확장 지점(04 문서 5장).
