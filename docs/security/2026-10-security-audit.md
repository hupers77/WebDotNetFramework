## 1. 요약

프레임워크의 기본 방어(SP 전용 DB 접근과 파라미터 바인딩, 전역 CSRF 검증, 기본 거부 권한 필터, `__Host-` 세션 쿠키와 DB 세션 확인, PBKDF2-SHA512 21만 회, CSP `script-src 'self'`, 파일 매직 넘버·GUID 저장, 실제 연결 주소로 검사하는 SSRF 차단)는 잘 갖춰져 있었다. 취약점은 주로 **게시판·첨부의 "기록 단위" 권한**(프로그램 권한은 맞지만 그 안의 다른 글·다른 사람 파일까지 닿는 문제)과 **최근 추가된 서식 편집기 필터의 서비스 거부**, **.NET 10.0.14 보안 업데이트 미적용**에서 나왔다.

## 2. 발견 취약점과 조치

### V-01 (높음) 게시판 댓글: 다른 게시판 권한으로 댓글 조회·등록·삭제

- **기준**: KISA 보안기능 '부적절한 인가', 주통기반 '불충분한 권한 검증', OWASP A01.
- **내용**: `/Board/{게시판}/Comments?id=`, `CommentSave`, `CommentDelete`는 주소의 게시판 권한만 확인하고, SP(`USP_COMMENT_*`)는 글 ID만 받았다. 그래서 게시판 A의 권한으로 게시판 B 글의 댓글을 다룰 수 있었다. 특히 A의 관리자(UPDATE)는 관리자 표시(`P_MANAGER_YN='Y'`)가 B에도 적용되어 **B의 비밀글 댓글과 익명 게시판 작성자 이름을 읽고, B의 댓글을 지울 수** 있었다(A의 DELETE 권한). 읽기만 가능한 사용자도 권한 없는 게시판 글의 댓글을 읽거나 달 수 있었다.
- **조치**: 세 SP에 `@P_BOARD_CD`를 추가해 글이 권한을 확인한 게시판의 글일 때만 처리한다(아니면 NOT_FOUND). 서비스·Controller가 게시판 코드를 넘긴다.
- **테스트**: `BoardSpTests` 다른 게시판 코드로 댓글 읽기·달기·지우기 거부(실제 DB), `BoardScreenTests` 게시판 코드 전달.

### V-02 (높음) 첨부·본문 사진: 볼 수 없는 글의 파일을 파일 번호로 다운로드

- **기준**: KISA '부적절한 인가', 주통기반 '파일 다운로드'·'불충분한 권한 검증', OWASP A01, 개인정보 안전성 확보조치(접근통제).
- **내용**: `/File/Download/{id}`, `/File/Image/{id}`, `/File/List`, `/File/DownloadZip`은 묶음 프로그램의 READ와 회사 격리만 확인했다. 게시글 첨부는 저장할 때 공유(`SHARE_YN='Y'`)되므로, 파일 번호(차례로 늘어남)만 바꾸면 **비밀글·공개 대상 회사를 지정한 글·게시기간이 지난 글·삭제된 글의 첨부와 본문 사진을 그 게시판 읽기 권한자 누구나 받을 수 있었다. 협력사 A가 협력사 B의 비밀 Q&A 첨부를 받는 것도 가능**했다(회사 간 정보 유출). 남이 작성 중인 임시 묶음도 같았다.
- **조치**: 새 SP `FW.USP_FILE_GROUP_ACCESS_GET`이 묶음의 기록 단위 권한을 돌려준다. 확정 전 임시 묶음은 올린 사람만, 게시글 묶음은 그 글을 볼 수 있는 사람만(`UFN_POST_VISIBLE`, 비밀글 포함) 볼 수 있다. FileController의 모든 조회 경로가 프로그램 권한 다음에 이를 확인하고, 볼 수 없으면 없는 것처럼 404로 답한다. 조회용 필터 색인 2개(`IX_TB_POST_FILE_GROUP`, `IX_TB_POST_IMAGE_GROUP`)를 추가했다.
- **테스트**: `BoardSpTests` 비밀글 묶음(작성자·관리자만, 다른 사용자·협력사 거부), 삭제된 글 묶음, 임시 묶음(실제 DB). `FileControllerTests` 목록·다운로드·사진·ZIP 404와 관리자 허용.

### V-03 (높음) 첨부 묶음 가로채기: 남의 묶음 ID를 내 글에 붙여 파일 획득

- **기준**: KISA '보안기능 결정에 사용되는 부적절한 입력값', 주통기반 '프로세스 검증 누락', OWASP A01·A04.
- **내용**: 글 저장(`USP_POST_SAVE`)이 화면에서 받은 `FILE_GROUP_ID`·`IMAGE_GROUP_ID`를 같은 프로그램인지 정도만 보고 확정했다. 남의 비밀글 묶음 ID를 넣어 내 글을 저장하면 그 파일이 내 글의 첨부가 되어 V-02 조치도 우회할 수 있었다.
- **조치**: 글 저장 SP가 묶음이 "이 글이 이미 가진 묶음"이거나 "내가 올린 확정 전 묶음"일 때만 받는다(아니면 NOT_FOUND). 같은 묶음을 첨부와 본문 사진에 함께 쓰는 것도 막았다. 업무 화면도 같은 확인을 하도록 개발 표준 가이드 첨부 절에 규칙을 추가했다.
- **테스트**: `BoardSpTests` 다른 글 묶음·남의 임시 묶음 거부, 관리자가 남의 글을 고칠 때 기존 묶음 유지(실제 DB).

### V-04 (중간) CREATE 권한만으로 남의 첨부를 지우거나 남의 묶음에 파일 추가

- **기준**: KISA '부적절한 인가', 주통기반 '불충분한 권한 검증'.
- **내용**: `/File/Delete`와 묶음 지정 업로드는 프로그램의 CREATE 또는 UPDATE만 확인했다. 글쓰기(CREATE)만 있는 사용자가 파일 번호로 **남의 게시글 첨부를 지우거나 남의 글에 파일을 끼워 넣을 수** 있었다.
- **조치**: 남이 만든 묶음에 파일을 더하거나 남이 올린 파일을 지우려면 UPDATE가 필요하다. CREATE만 있으면 자기 묶음·자기 파일만 다룬다(403).
- **테스트**: `FileControllerTests` 업로드(내 묶음 CREATE 허용, 남의 묶음 CREATE 거부·UPDATE 허용), 삭제(자기 파일 CREATE 허용, 남의 파일 CREATE 거부).

### V-05 (중간) 게시글 HTML 필터 정규식 서비스 거부(ReDoS)

- **기준**: KISA 시간 및 상태 '종료되지 않는 반복문'(자원 고갈), OWASP A04, 가용성.
- **내용**: 서식 편집기 내용을 거르는 `HtmlSanitizer`의 태그 정규식이 닫히지 않은 태그마다 끝까지 다시 훑어 입력 길이의 제곱으로 느려졌다. 측정: `<a`를 반복한 2만 자 1.7초, 4만 자 6.2초, **8만 자 24.6초**(글 내용 한도 20만 자면 1건에 수 분). 로그인한 사용자 몇 명이 글 저장 요청을 보내면 웹서버 CPU를 붙잡을 수 있었다. 닫는 태그 찾기도 남은 문자열을 매번 복사했다.
- **조치**: 태그 안에 `<`가 오면 그 자리에서 멈추게 바꿔 길이에 비례한 시간에 끝나게 했다(그런 태그는 글자로 인코딩하므로 결과는 더 안전한 쪽으로만 달라진다). 닫는 태그 찾기는 복사 없이 찾는다. 결과: 20만 자 입력 모두 수 밀리초.
- **테스트**: `HtmlSanitizerTests` 병적 입력 4종 20만 자 2초 안, 꺾쇠가 든 속성·닫는 태그 공백 처리.

### V-06 (높음) .NET 10.0.14 보안 업데이트 미적용 (알려진 취약점, CVE)

- **기준**: OWASP A06 '취약하고 오래된 구성요소', 설계서 9장 '취약 구성요소'.
- **내용**: 2026-10-25 .NET 10.0.14 긴급(대역 외) 보안 업데이트가 나왔다. 프로젝트는 10.0.13 패키지를 쓰고 있었다.

  | CVE | 내용 | 이 시스템 영향 |
  | --- | --- | --- |
  | CVE-2026-111497 | Brotli 디코더 범위 밖 쓰기 (서비스 거부·정보 노출·권한 상승) | 요청 압축 해제·HttpClient 자동 압축 해제를 쓰지 않아 직접 경로는 없음. 런타임 공통 구성요소라 업데이트 필요 |
  | CVE-2026-70197 | SocketAsyncEventArgs 메모리 손상 (10/13 패치가 불완전해 재발행) | 모든 네트워크 처리(Kestrel·IIS 프로세스 내 호스팅, SqlClient)에 해당. **서버 런타임 업데이트 필수** |

### V-07 (낮음) 검증 오류 응답에 내부 형식 이름·경로 노출

- **기준**: KISA 에러처리 '오류 메시지 정보노출', 주통기반 '정보 누출'.
- **내용**: 형식이 틀린 JSON을 보내면 응답 메시지에 `The JSON value could not be converted to System.Int64. Path: $.postId | LineNumber...` 같은 프레임워크 문구가 그대로 나갔다.
- **조치**: 검증 메시지는 메시지 키 형식(`MSG.INVALID_INPUT` 등)일 때만 돌려주고, 그 밖의 문구는 일반 입력 오류로 바꾼다. 테스트: `WebPipelineTests`, `RequestRulesTests`.

### V-08 (낮음) `/health`가 로그인 없이 애플리케이션 버전을 알려 줌

- **기준**: 주통기반 '정보 누출'. **조치**: 버전은 서버 자신(루프백)에서 부를 때만 준다. 외부에는 `{"status":"Healthy"}`만.

### V-09 (낮음) HSTS 기간이 기본값 30일

- **기준**: 주통기반 '데이터 평문 전송', 설계서 9장 보안 헤더 기본값(1년 + 하위 도메인). **조치**: `max-age=31536000; includeSubDomains`(운영 환경). 포털 도메인의 하위 도메인에 HTTP 전용 사이트가 있으면 배포 전에 알려 달라(R-05).

### V-10 (낮음) IIS `web.config` 보안 설정 없음

- **기준**: 주통기반 '디렉터리 인덱싱'·'정보 누출'·'불필요한 Method 악용'. 설계서 9장은 `Server`/`X-Powered-By` 제거와 디렉터리 목록 비활성을 IIS 몫으로 두었으나 저장소에 설정 파일이 없었다.
- **조치**: `src/Portal.Web/web.config` 추가(게시 결과에 포함 확인): `Server` 헤더 제거(`removeServerHeader`), `X-Powered-By` 제거, 디렉터리 목록 끔, TRACE·TRACK·WebDAV 메서드 거부, `App_Data`·`keys`·`logs` 숨김, 요청 본문 30MB·URL 길이 한도.

### V-11 (낮음) SSRF 차단의 우회 가능 주소 대역

- **기준**: KISA '서버사이드 요청 위조', 주통기반 'SSRF', OWASP A10.
- **내용**: 송신 API 주소 정책이 IPv4를 품은 IPv6 중 NAT64(`64:ff9b::/96`)와 6to4(`2002::/16`)를 풀어 보지 않았고, 시험 대역(192.0.0/24, 198.18/15)을 공인으로 봤다. NAT64 환경이면 `64:ff9b::7f00:1`로 루프백에 닿을 수 있었다.
- **조치**: 안의 IPv4로 다시 검사하고 시험 대역을 사설로 본다. 테스트: `OutboundAddressPolicyTests`.

### V-12 (낮음) PDF 변환 차단 정책이 `<header>`가 있는 문서에서 본문에 들어감

- **내용**: PDF 변환은 외부 자원을 막는 CSP를 `<head` 바로 뒤에 넣는데, `<header>`도 `<head`로 보아 본문에 넣으면 브라우저가 정책을 무시한다(현재 서식은 `<head>`가 먼저라 실제 영향 없음). **조치**: 이름이 정확히 `head`인 태그만 찾는다. 테스트: `PdfDocumentTests`.

### V-13 (낮음) 업로드 차단 확장자 보강

- **기준**: KISA '위험한 형식 파일 업로드', 주통기반 '악성 파일 업로드'. 허용 목록(공통코드 `FILE_EXT`)이 1차 방어라 위험은 낮다.
- **조치**: 관리자가 실수로 허용해도 막는 목록에 mht·mhtml·xht·xsl·chm·pif·msc·application·inf·scf·url·iso·img·vhd(x)·appx·msix·phtml·jspx·asa·war·swf·jnlp 등을 더했다.
