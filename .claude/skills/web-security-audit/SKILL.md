# 웹 보안 점검 (KISA·보호나라·주통기반·OWASP)

이 skill은 2026-10 WebDotNetFramework 보안 점검(`docs/security/2026-10-security-audit.md`)을 다른 시스템에도 똑같이 하도록 정리한 절차다. 대상 언어·프레임워크는 가리지 않는다(.NET, Java/JSP, PHP, ASP, Node, Python).

이 폴더에 있는 것:

- `references/checklist.md`: 점검 항목(주통기반 웹 21, KISA 보안약점 49, 서버·운영, 개인정보)과 항목별 확인 방법
- `references/report-template.md`: 보고서 양식
- `scripts/Invoke-SourceScan.ps1`: 소스에서 알려진 취약 패키지와 위험한 코드 패턴 후보를 찾는다
- `scripts/Test-WebSecurity.ps1`: 접속 주소에 안전한 요청만 보내 헤더·쿠키·메서드·노출 경로·오류 화면·TLS를 확인한다

스크립트는 PowerShell 5.1(Windows 기본)과 PowerShell 7에서 돈다. 스크립트가 없는 PC라면 `references/checklist.md`의 명령으로 같은 확인을 한다.

## 0. 시작 전에 정할 것 (안전 규칙)

1. **대상과 권한**: 점검할 저장소 경로나 접속 주소, 그리고 그 시스템을 점검해도 된다는 사용자 확인이 있어야 한다. 사용자 소유나 사내 시스템이 아니면 하지 않는다.
2. **운영 서버에는 안전한 요청만** 보낸다(GET, HEAD, OPTIONS, TRACE 한 번씩). 로그인 시도 반복, 무차별 대입, 부하, 데이터 변경, 실제 공격 페이로드 전송은 하지 않는다. 공격 재현은 로컬이나 개발계, 또는 테스트 코드로 한다. 운영 동적 진단(모의해킹)은 전문기관 몫이고 보고서 권고로 남긴다.
3. **비밀값**: 점검 중 비밀번호·키·연결 문자열을 찾으면 보고서에는 위치와 종류만 쓰고 값은 쓰지 않는다. 개인정보가 든 실제 데이터는 열람하지 않는다.
4. **범위**: 사용자가 말한 범위(예: 업무 영역만)를 지킨다. 패치는 사용자가 요청했을 때만 하고, 저장소 규칙(`CLAUDE.md`, 테스트 규칙, 허용 패키지 목록)을 따른다.
5. 이 저장소가 프레임워크에서 갈라진 업무 저장소라면, **프레임워크 소유 파일의 취약점은 고치지 말고** 보고서에 "프레임워크 저장소에 반영 필요"로 적는다.

## 1. 대상 파악 (먼저 지도를 그린다)

소스가 있으면 다음을 짧게 정리하고 보고서 "대상" 칸에 쓴다.

- 언어·런타임 버전(예: `global.json`, `pom.xml`, `composer.json`, `package.json`)과 웹 서버(IIS, Tomcat, Apache, Nginx)
- 진입점: 컨트롤러·라우트·JSP/ASP 페이지, 로그인 없이 열리는 주소, 관리 화면 경로, 외부 API
- 인증·세션·권한 방식(필터, 어노테이션, 미들웨어)과 **기록 단위 권한**을 어디서 확인하는지(SP, 서비스, 쿼리 조건)
- DB 접근 방식(SP, ORM, 직접 SQL)
- 파일 올리기·받기, 서식 편집기(HTML 본문), 외부로 나가는 호출(SSRF), 메일, 엑셀·PDF 변환
- 설정 파일(`web.config`, `appsettings*.json`, `application.properties`, `.env`)과 비밀값 주입 방식
- 개인정보 항목과 저장 방식(암호화, 마스킹), 접속 기록 보관

## 2. 자동 점검 (후보 찾기)

```powershell
# 소스: 취약 패키지(dotnet/npm/pip/composer) + 위험 패턴 후보
pwsh -File .claude/skills/web-security-audit/scripts/Invoke-SourceScan.ps1 -Path . -OutDir ./security-scan

# 접속 주소: 개발계부터. 운영은 운영 담당 동의 후
pwsh -File .claude/skills/web-security-audit/scripts/Test-WebSecurity.ps1 -Url https://dev-portal.example.local -OutFile ./security-scan/web.md
```

- 결과는 **후보**일 뿐 판정이 아니다. 코드를 열어 실제로 사용자 입력이 닿는지 따라가서 판정한다.
- 패턴이 없다고 안전한 것도 아니다. 권한 우회(IDOR)와 업무 흐름 우회는 패턴으로 잡히지 않으므로 3장에서 직접 본다.
- **알려진 취약점(CVE)**: 런타임·프레임워크 버전을 확인하고, 그 제품의 공식 보안 공지(예: .NET 릴리스 노트, Tomcat·Spring·PHP 보안 공지, 보호나라 보안 공지)에서 현재 버전 이후 보안 수정이 있는지 찾는다. 웹 검색이 되면 최신 공지를 확인하고, 안 되면 확인하지 못했다고 보고서에 쓴다.

## 3. 직접 점검 (이번 점검에서 실제 취약점이 나온 곳부터)

`references/checklist.md`의 모든 항목을 보되, 다음은 반드시 코드를 따라가며 확인한다. 2026-10 점검의 높음 등급은 모두 여기서 나왔다.

1. **기록 단위 권한(IDOR)**: 화면 권한(프로그램·메뉴)만 확인하고, 그 안의 **다른 사람·다른 회사·다른 게시판의 기록**을 번호만 바꿔 다룰 수 있는지 본다. 한 건 조회·수정·삭제와 첨부 받기 경로마다 확인한다.
2. **자식 기록이 부모에 속하는지**: 댓글·상세 행·첨부를 다루는 쿼리가 "권한을 확인한 부모"와 연결되는지 본다(예: 게시판 A의 권한으로 게시판 B 글의 댓글을 다루는 경우).
3. **화면이 넘긴 ID를 저장에 쓰는 곳**: 첨부 묶음 ID, 결재 문서 ID, 상위 기록 ID처럼 화면이 보낸 ID를 그대로 연결하면 남의 것을 가로챌 수 있다. 서버가 "내 것이거나 이 기록이 이미 가진 것"인지 확인하는지 본다.
4. **올리기·지우기 소유권**: 쓰기 권한만으로 남이 올린 파일을 지우거나 남의 묶음에 더할 수 있는지 본다.
5. **HTML 필터·정규식**: 서식 편집기 본문을 거르는 코드의 정규식이 긴 입력에서 오래 걸리지 않는지 본다. 의심되면 수만 자 입력으로 시간을 재 본다(로컬).
6. **오류·상태 응답의 정보 노출**: 검증 오류 문구, 상태 확인 주소(`/health`, `/actuator`)의 버전, 예외 화면, `Server`·`X-Powered-By` 헤더를 본다.
7. **플랫폼 패치 수준**: 런타임·패키지가 최신 보안 릴리스인지, 빌드 SDK와 서버 런타임이 둘 다 맞는지 본다.
8. 그 밖의 기본: SQL 삽입, XSS, CSRF, 파일 업로드 검증, 경로 조작, SSRF, 세션·쿠키, 비밀번호 저장, 비밀값 하드코딩, 로그의 개인정보.

**발견하면 먼저 증명한다**: 실패하는 테스트(권한 우회 시나리오, 시간 측정)를 쓰거나 로컬에서 재현한 뒤 고친다. 재현하지 못한 것은 "의심"으로 적고 등급을 낮춘다.

## 4. 패치 (사용자가 요청했을 때)

- 한 취약점에 한 가지 최소 수정을 한다. 서버(DB·서비스)에서 막고, 화면에서 숨기는 것만으로 끝내지 않는다.
- 권한이 없으면 403보다 404(없는 것처럼)를 우선한다. 기록이 있는지조차 알려 주지 않기 위해서다.
- 테스트를 함께 넣는다: 거부되어야 할 경우와 정상 경우 둘 다.
- 패키지는 같은 주 버전의 보안 패치로 올리고, 허용 패키지 목록이 있으면 지킨다.
- 서버 설정(IIS·TLS·방화벽)처럼 저장소 밖에서 할 일은 고치지 말고 권고(R-번호)로 남긴다.
- 저장소 규칙대로 단위 테스트를 돌리고, DB를 바꿨으면 실제 DB 통합 테스트도 돌린다. 고치기 전부터 실패하던 테스트는 기준 브랜치에서도 실패하는지 확인해 따로 적는다.

## 5. 보고서

`references/report-template.md` 양식으로 `docs/security/<YYYY-MM-DD>-security-audit.md`를 쓴다(저장소가 없으면 사용자가 정한 곳).

- 항목마다 판정을 하나 단다. **양호**(기준 충족), **취약**(이번에 찾음. 고쳤으면 "조치"), **권고**(개선 권장), **운영 확인**(코드 밖, 서버에서 확인), **해당 없음**.
- 취약점은 V-번호, 등급(높음/중간/낮음), 기준(KISA 항목, 주통기반 번호, OWASP), 내용, 재현 방법(위험하지 않게 요약), 조치, 테스트를 쓴다.
- 운영 권고는 R-번호, 담당(운영·인프라·보안·개발), 시점(즉시·배포 시·오픈 전·정기)을 쓴다.
- 요약 표에는 등급별 건수를 넣고, 사용자에게는 높음 등급과 사용자가 직접 할 일(서버 패치 등)부터 말한다.

## 6. 마무리

- 패치를 했으면 PR/MR 하나로 올리고 본문에 V-번호별 변경과 테스트 결과를 적는다.
- 단계 종료 때 다시 볼 것(브라우저·실서버 확인)은 저장소의 확인 목록이 있으면 그곳에 한 줄씩 남긴다.
- 업무 저장소라면 프레임워크 쪽 문제를 따로 모아 프레임워크 저장소에 전달한다.
